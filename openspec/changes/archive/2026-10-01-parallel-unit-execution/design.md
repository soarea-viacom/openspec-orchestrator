# Design

Paths: `<state>` = `<store>/.orchestration/state`; `<ws>` = `<store>/.orchestration/workspaces`; `<udir>` = `<state>/<name>.units`.

### D1. Unit model: four flat fields, two reuse the seam dialect

- `units: "<u>=<file>,<file>;<u>=<file>"` — exactly the `seams` dialect, so the disjoint-files check reads both the same way. `unit_deps: "<u>=<dep>,<dep>;..."` — same `name=list;name=list` dialect (units with no deps omitted), so one parser serves `units`, `unit_deps`, `unit_tasks`: `map_keys <value>` and `map_get <value> <key>` in lib.sh. `unit_tasks: "<u>=1.1,1.2;..."` — tasks.md ids per unit. `ui_units: "<u>,<u>"`.
- Rejected: `unit_deps: "<u>><dep>"` — a second separator for the same shape needs a second parser. Rejected: one combined field (`<u>=files|deps`) — breaks the seam dialect, so the disjoint-files reading no longer applies unchanged.
- Unit names: `^[a-z0-9]+(-[a-z0-9]+)*$`, checked by `units check` (kebab-case keeps `<name>.<unit>` unambiguous, D2).
- `units_check <slug> <name>` (lib.sh) is state-only and replaces an LLM critique of the split: every dep names a unit; deps acyclic; every unit file appears in some `seams` list (a missing one is a seam-list finding); two units whose file lists overlap must be ordered by a dep path; every unit has ≥1 file; a task id in two units is an error. `next` calls only this function. The CLI `units check` runs it and then reads `change_dir`'s tasks.md, printing ids (`- [ ] N.M` / `- [x] N.M`) assigned to no unit as `unassigned: <id>` (not an error — manual tasks stay unassigned); the orchestrator runs the CLI once after writing the split. Rejected: a `units_checked: yes` flag that `next` trusts — a later `state set units ...` would leave a stale flag; rerunning the state-only check costs nothing. Rejected: a `max` critique of the split per "Critique beyond the spec" — the properties that matter (acyclic, ordered overlap, coverage) are mechanical, and an LLM round costs minutes before any worker starts.
- Overlap is allowed only along a dep path because a dependent's worktree is created after its dep merged (D3), so it starts from the dep's code; two concurrent units never share a file.
- `split` (D7) at tier `deep` (the generator). `lifecycle: light` and `parallel: false` instead run `units single [--ui]` (none tier): `units: all=<union of seam files>`, `unit_tasks: all=<every task id>`, `ui_units: all` with `--ui`.

### D2. Per-unit worktree and branch

- Path: `workspace_path <slug> <name> [<unit>]` → `<ws>/<name>` or `<ws>/<name>.<unit>`; still the only builder of workspace paths. Change names are kebab-case, so `.` cannot collide with another change's directory.
- Branch: `unit_branch <name> <unit>` → `change/<name>.<unit>`. Rejected: `change/<name>/<unit>` — git stores `change/<name>` as a ref file, so `change/<name>/<unit>` fails with a directory/file ref conflict while the change branch exists.
- `unit create --store --project --name --unit`: refuses an unknown unit, an existing unit file with status other than `pending`, deps not all `merged`, or a dirty change worktree (`git -C <ws>/<name> status --porcelain` non-empty — a unit `base` must hold everything the change branch has); `git worktree add -b change/<name>.<u> <ws>/<name>.<u> change/<name>`; writes `<udir>/<u>.yaml` (`status: running`, `iterations: 0`, `base: <sha>`, `checks_commit: ""`, `screenshot: ""`, `critique: ""`, `merge_attempts: 0`). Unit writers always run at `standard` (no tier option): Verify's no-history assumption (implementer = `standard`, D5) then holds by construction. Rejected: `unit create --tier` — a non-standard unit writer would be invisible to `verify_pick`, which ignores `phase=unit` entries. `unit remove`: `worktree remove --force` + `branch -D`, status unchanged. `workspace remove` removes every `<ws>/<name>.*` worktree and `change/<name>.*` branch first.
- `apply` (D7) is where the change worktree is made clean for every change: the orchestrator commits whatever `git status --porcelain` shows in `<ws>/<name>` (proposal artifacts in local mode, anything else left behind; trailer `Change: <name>`) before recording `applying`. A pre-1.4.0 change resumed at `applying` skips `apply` and may hold uncommitted wave edits from old Apply, so before acting on `split` the orchestrator likewise commits whatever `git status --porcelain` shows in `<ws>/<name>` (trailer `Change: <name>`); `unit create` refusing a dirty change worktree makes a missed commit fail loudly instead of silently dropping that work from every unit's `base`. Rejected: refusing `split` itself — `next` reads state only and cannot see the worktree.
- `gate run --unit <u>` runs `gate_quick`/`gate_full` in the unit worktree and never writes `gate_tree` (that field means the change branch's tree).
- **Unit workers commit.** A unit worker is the only writer in its worktree and the only user of its index and branch, so the shared-index hazard behind "workers never commit" does not exist; worktrees of one repo have separate indexes and HEADs, and ref updates are locked by git. It commits the checks (D4) and each green iteration with `git add -- <its files>` (never `-A`) and trailers `Change: <name>`, `Unit: <u>`. Never push, rebase, merge, checkout, reset, or touch another branch. Rejected: orchestrator commits per unit — it would have to stop every unit at each iteration, serializing the units, and the critic needs per-iteration commits to see the checks-first history. All other workers keep the no-git-write rule.

### D3. Scheduler and per-unit state files

- Unit state lives in `<udir>/<u>.yaml`, state-module dialect (`state_field`/`state_write`). Rejected: one flat field in the change file (`unit_status: a=running;b=green`) — workers call `unit iterate` concurrently, and `state_write` is read-modify-write, so two workers would lose each other's updates; per-unit files give each writer its own file. `status` globs `<state>/*.yaml` only, so unit files are never read as changes; it gains a `UNITS` column `<merged>/<total>` (`-` with no units). Session-log appends stay shared (one `>>` line < PIPE_BUF is atomic).
- Status values: `pending` (no file) → `running` → `green` → `reviewing` → `reviewed` → `merged`; `failed`; `conflict` → `resolving` (orchestrator, before dispatching the conflict agent) → `merged`/`failed`. `unit set --unit <u> key value ...` (generic, via `set_record`) and `unit get --unit <u>`.
- Capacity: `unit_capacity` = `orchestration.unit_concurrency`, else `orchestration.concurrency`, else 1. Rejected: reusing `concurrency` alone — it caps changes per project, a different resource; one key per resource, defaulting to the old one so unconfigured stores behave as requested. A unit with status `running`, `reviewing`, `conflict`, or `resolving` holds a slot: each may receive a writer again (worker, revising worker, conflict agent) until it is `reviewed`, `merged`, or `failed`. So `unit-revise` and `merge-conflict` reuse the slot the unit already holds and never exceed capacity. Rejected: counting `running` only — a slot freed during review is refilled by `unit-spawn`, and a blocking critique then re-dispatches the revising worker on top: cap+1 writers.
- `units next --store --name` prints `ready: <u> ...` (pending units whose deps are all `merged`, in `units` field order, at most the free capacity), `running: <u> ...` (status `running`, `reviewing`, `conflict`, or `resolving` — the slot holders), `capacity: <free>` (`unit_capacity` minus the slot holders). Field order is the tie-break: deterministic and controlled by the generator. Rejected: alphabetical — the generator cannot express priority.
- `units list` prints `<u> <status> <iterations>` per unit in field order.

### D4. Check-first worker contract

- Worker inputs (dispatch prompt): proposal + delta spec, the unit's task ids and their tasks.md text, its file list, worktree path, engine path, the commands below. Step 1, before any implementation: write executable checks — unit tests in the project's own runner for each requirement the unit's tasks implement; for a UI unit, a Playwright script. Commit them, then `unit checks-done --unit <u>` records `checks_commit` (refused while HEAD = `base`). `unit iterate` refuses until `checks_commit` is set. The critic reads `git diff base..checks_commit` to confirm checks preceded code.
- Playwright script (UI unit): `playwright` (the library, run by the project's own test runner, so it is part of `gate_quick`) launches Chromium at 1280×800 on the page, writes a full-page screenshot to `$UNIT_SCREENSHOT` only when `$UNIT_NAME` equals the unit that owns that test (both exported by `unit iterate`, D5; the harness takes the owner name as an argument; a non-owning test, or any test with `UNIT_NAME` unset as under `gate_full`, still runs and asserts but writes no file), so the recorded PNG is always the iterating unit's own view — `node --test` runs every `*.ui.test.js` in the worktree, including those of already-merged units, and asserts: the board/canvas element's bounding box lies inside the viewport; `document.documentElement.scrollWidth <= innerWidth`; every SVG shape has computed `fill` or `stroke` other than `none`/transparent; for a DOM-grid board, every cell has a non-transparent computed background; plus one assertion per requirement the unit implements (e.g. a new panel is visible, inside the viewport, and does not intersect the board's box). The checks must be in what `gate_quick` runs (for chess-game, `npm test` runs every `*.test.js`).
- Dependency rule: `playwright` is the one dependency a worker may add, as a target-project devDependency, only when the unit is in `ui_units` and the project lacks it; `package.json`/lockfile must then be in that unit's file list (so `units check` orders every other unit touching them after it) and the addition shows in the Gate 2 diffstat. The browser binary (`npx playwright install chromium`) is a machine-level cache download outside the project, done once before a run with the human's approval. The engine never depends on Playwright. Rejected: engine-side Playwright runner — every target project would inherit a Node dependency through the engine.
- Loop: implement → `unit iterate --unit <u>` (the engine runs the checks) → fix, at most 5 iterations. The worker never reports its own result.

### D5. Iteration cap in the engine

- `unit iterate --store --project --name --unit` (`UNIT_ITER_CAP=5` in lib.sh): refused while `checks_commit` is empty; n = iterations+1; n > 5 → no write except `status: failed`, exit non-zero ("iteration cap"). Else it runs `gate_command quick` in `<ws>/<name>.<u>` with `UNIT_SCREENSHOT=<udir>/<u>/screenshot-<n>.png` (absolute, dir created) and `UNIT_NAME=<u>` exported, and sets r = `green` on exit 0, else `red`; for a UI unit, r = `green` also requires that PNG to exist afterwards (missing → r = `red`). Then it appends `role worker phase unit unit <u> event iterate iteration <n> checks <r> tier standard model <model_for_tier standard>`, writes `iterations: n` and, when the PNG exists, `screenshot: <its absolute path>`; r = green → `status: green`; red at n = 5 → `status: failed`. It prints the gate output and exits 0 on green, 1 on red. Rejected: `--result green|red` passed by the worker — every other result in the engine comes from a command the engine ran (`gate run`), and a worker that skipped or misread its checks would put a red unit in front of the critic. `unit screenshot-path` is dropped: the engine owns the path.
- Session entry shapes (all `phase=unit`; worker and critic entries carry `unit`, `tier`, `model`; orchestrator entries carry no tier): spawn `role worker phase unit unit <u> event spawn tier standard model <m> transcript_id <id>` (orchestrator, at `unit-spawn` and `unit-revise`); iteration (written by `unit iterate`, above); critic `role critic phase unit unit <u> event critique iteration <n> tier <t> model <m> transcript_id <id>` (orchestrator, at `unit-critique`); conflict agent `role worker phase unit unit <u> event merge-conflict tier standard model <m> transcript_id <id>`; merge `role orchestrator phase unit unit <u> event merge result merged|conflict|failed` (written by `unit merge`, D8); `role orchestrator phase unit event units-merged` (orchestrator, when acting on `units-merged`). With these, every edge of the critical path (spawn → iterate → critique → merge → units-merged) has a logged `ts`. `phase=unit` matches neither `applying|checking` nor `proposed`, so `implementer_*`/`proposer_*` ignore unit entries; every unit writer runs at `standard`, which is exactly what `verify_pick` assumes with no `applying|checking` entry, so Verify resolves to `deep`; a later fix round logs `phase checking` as today. Rejected: logging unit writers as `phase applying` — the critic entries share `phase=unit` and would then need a role filter in `last_session_field`. `status`'s `LAST_TIER` reads the last entry that has `tier=`.
- Rejected: counting iterations in the worker's prose — the cap must survive a worker that miscounts.

### D6. Critic over green units

- Tier: `critic_pick` (one above the logged proposer: `max` under full, `deep` under light), as the request specifies. Rejected: Verify's implementer-based tier (`deep` over `standard` workers) — the request ties the unit critic to the proposer; it also makes the unit review a stronger read than the change-level Verify that follows. Cost: one `max` call per unit under full (4 in the demo) instead of `deep`.
- `units ready-for-review` prints, per green unit with empty `critique`, `unit: <u>` then `screenshot: <abs path>` for every `<udir>/<u>/screenshot-*.png` in iteration order. Before dispatch the orchestrator sets `status reviewing`, so a repeated `next` does not re-dispatch.
- `model critic --unit <u>` prints the model id, then `checker_inputs unit-critic`: proposal + delta spec; unit files and task ids (`unit get` / `units` field); unit diff `git diff <base>..change/<name>.<u>` and checks diff `<base>..<checks_commit>`; screenshots listed by `units ready-for-review`, each opened with an image-capable read; prior unit critique. Same "no codebase exploration" line.
- Report `<udir>/<u>.critique.md`; it must quote each screenshot path it viewed. `unit set --unit <u> critique <r>` for a UI unit refuses unless the report exists and contains the unit file's `screenshot` value (the absolute path `unit iterate` recorded for the latest green iteration) as a fixed-string match (`grep -F`). Pass (`clean`/`warnings:<m>`) → orchestrator sets `critique <r> status reviewed`; warnings are not swept per unit — the change-level Verify and sweep (full) run over the merged branch anyway, and the report is listed at Gate 2. `blocking:<n>` → `next` returns `unit-revise` if iterations < 5 (orchestrator sets `status running critique ""`, resumes or re-dispatches the worker with the report; its iterations continue under the same cap), else `gate1`.

### D7. next_action at `applying`

`awaiting-acceptance`/`accepted` → `apply` with tier `none`, model `-`, `set_phase: applying`, reason "commit everything `git status --porcelain` shows in the change worktree, record phase applying, then call next: the split follows". Rejected: keeping `apply standard <model>` — `next` names the worker the orchestrator dispatches, so it would spawn an unsplit implementer into the change worktree. At `applying`, evaluated top-down; every output other than `split` adds `running: <slot holders>` (possibly empty):

| condition | action | tier | extra |
|---|---|---|---|
| `units` empty, `lifecycle full`, parallel | `split` | `deep` | reason: write `units`/`unit_deps`/`unit_tasks`/`ui_units`, run `units check` |
| `units` empty, light or `parallel false` | `split` | none | reason: run `units single` (`--ui` if the change has UI) |
| `units check` fails | exit non-zero with its message | | |
| a unit `failed` | `gate1` | none | reason names the unit and cause |
| a unit `conflict` | `merge-conflict` | `standard` | `units: <u>`; set `status resolving`, one agent in that worktree, conflicting files only, then `unit merge` again |
| `reviewing` + `critique blocking:*`, iterations < 5 | `unit-revise` | `standard` | `units: <u>` |
| same, iterations ≥ 5 | `gate1` | none | |
| `reviewed` with all deps `merged` | `unit-merge` | none | `units:` in `units merge-order` order |
| `green`, `critique` empty | `unit-critique` | critic tier | `units:`; set `status reviewing` first |
| `units next` ready non-empty | `unit-spawn` | `standard` | `units:`; per unit `unit create`, then one Agent |
| any `running`/`reviewing`/`resolving` | `wait` | none | reason: call `next` when a worker or critic returns |
| all `merged` | `units-merged` | none | `set_phase: checking` |
| otherwise | exit non-zero (`units stalled`) | | |

- One action per call keeps `next`'s "one step" contract; the `running`/`reviewing` statuses make the repeated call return the next undispatched step, so the orchestrator spawns, reviews and merges concurrently by calling `next` after each dispatch. Rejected: one `action: units` listing ready/running/review/merge together — several tiers in one output, and tests could not assert a single branch.
- `next_action` calls only the state-only `units_check` (D1) and reads unit files, which are state files; it still reads only state + session log, never tasks.md or a worktree.
- Light: `split` none-tier → one unit `all` → same loop; the unit worker is the resumed proposer when the host can resume, else a fresh `standard` worker (the existing light Apply rule). The unit critic runs under light too (`deep`): it is the only check that looks at screenshots.

### D8. Merger: none-tier bash, agent only on conflict

- Integration happens inside the units loop, not in `merge-lane run`: a dependent's worktree must start from its deps' code (D1), so deps have to land on `change/<name>` before dependents spawn. Rejected: rebasing every unit at merge-lane time — dependents could never start, and merge-lane would mix unit integration with trunk integration. `merge-lane run` is unchanged.
- `units merge-order`: Kahn's algorithm over `unit_deps`, ties by `units` field order, cycle → exit non-zero naming the units.
- `unit merge --store --project --name --unit`: requires status `reviewed` or `resolving` and every dep `merged`; from `resolving` with a rebase still in progress in the unit worktree (`git -C <unit-wt> rev-parse --git-path rebase-merge` or `rebase-apply` exists — the conflict agent did not finish), it runs `rebase --abort`, sets status `failed`, and exits 3 (regardless of `merge_attempts`); `git diff --name-only $(merge-base change/<name> <ub>)..<ub>` ⊆ the unit's files, else exit non-zero ("outside unit files: ..."; a seam-list finding); change worktree clean; `git -C <unit-wt> rebase change/<name>`; on conflict: list `--diff-filter=U` files, `rebase --abort`, `merge_attempts+1`, status `conflict` (or `failed` when `merge_attempts` was already 1), exit 3. On success: `git -C <change-wt> merge --ff-only <ub>`; tick the unit's `unit_tasks` in `change_dir`'s tasks.md (`- [ ] N.M` → `- [x] N.M`; when that file is inside the change worktree, commit it with `Change:` trailer); `unit remove`; status `merged`. Every rebase attempt appends the `event merge` session entry (D5); refusals (status/dep/scope/dirty checks) log nothing. Workers never edit tasks.md — concurrent units would share it.
- Conflict agent: `standard`, one attempt, in the unit worktree only, `git rebase change/<name>`, resolves only the files `unit merge` printed, `git rebase --continue`; then the orchestrator runs `unit merge` again. Rejected: always an agent — rebase + ff + scope check is deterministic, and the scope check plus dep-ordered overlap make conflicts rare. It logs the conflict-agent entry (D5).
- After `units-merged`: `checking` as today — `gate_full` + Verify on the change branch (the "rerun the full suite"), fix rounds in the change worktree, `tasks-open`, Archive, merge lane, Gate 2, squash-merge.

### D9. Single-worker baseline

- `parallel` is a per-change state field (`cmd_state_init` writes `""`); empty reads `orchestration.parallel` from the store config; empty there reads `true`; other values → `next` exits non-zero. `false` → `split` none-tier `units single`. Rejected: store-config-only toggle — two runs in one store (demo) would need a config edit between them; rejected `--single` flag on `next` — `next` is read-only and must derive everything from state.

### D10. Demo on chess-game

- chess-game: all UI is inline in `index.html` (DOM-grid board `#board-wrap`, no SVG/canvas), `engine.js` rules, no `.gitignore`, no remote. Three features would all collide in `index.html`, so the split is:
  - `ui-hooks` (root): `index.html` (plugin registry: inline script calls each `window.ChessUIPlugins[i].render(ctx)` after `render()` and `reset(ctx)` on new game/undo; mount points `#side-panels`, `#plugin-controls`; `<script>` tags for the three plugin files), `.gitignore` (`node_modules/`), `package.json`, `package-lock.json` (`playwright` devDependency), `ui-harness.js` (`runUiCheck(owner, page, asserts)`: launch, generic invariants, screenshot to `UNIT_SCREENSHOT` only when `UNIT_NAME === owner`; each `<feature>.ui.test.js` passes its own unit name), `ui-hooks.ui.test.js`.
  - `captured-pieces` → deps `ui-hooks`: `captured-pieces.js`, `captured-pieces.test.js`, `captured-pieces.ui.test.js`.
  - `move-clock` → deps `ui-hooks`: `move-clock.js`, `move-clock.test.js`, `move-clock.ui.test.js`.
  - `board-flip` → deps `ui-hooks`: `board-flip.js` (CSS rotate on `#board-wrap` and its children), `board-flip.test.js`, `board-flip.ui.test.js` (after the click, a1's box is in the board's top half).
  - Each plugin file is `require`d by its own test, so knip sees it as used.
- Demo store config: `orchestration.unit_concurrency: 3` so the three features run at once (`concurrency: 2` stays for changes).
- Runs: parallel change `chess-trio` first, held at Gate 2 (not merged); then `chess-trio-single` from the same trunk commit with `parallel false` and a copy of `chess-trio`'s accepted change directory (same proposal, so Propose variance is excluded), brought to `awaiting-acceptance` (Gate 0 shows the resume noting the byte-identical baseline copy with `parallel false`; human accepts) — the human's acceptance of `chess-trio`'s Gate 0 covers this byte-identical copy (task 4.3); its Gate 2 is declined and `workspace remove` discards it; then `chess-trio`'s Gate 2 is answered. Running the parallel one first gives the baseline the warmer caches, which biases against the parallel claim. Prep before either timer: `npx playwright install chromium` and `npm cache add playwright` (downloads; human approves).
- Shape of the parallel run (stated in the report so a < 3× ratio is read correctly): `ui-hooks` runs alone first (all UI lives in one `index.html`; the alternative is three units colliding on it), so the critical path is `ui-hooks` (iterations + `max` critique + merge) → the longest of the three features (iterations + `max` critique) → three merges → `checking`. The parallel run spends 4 `max` critic calls, the baseline 1. The iteration cap applies per unit in both runs by design, so the baseline's one unit carries four units' work under the same cap of 5; a baseline that ends `failed` → `gate1` is reported as the result, with its iteration log — no retry, no cap change.
- Timing: `session append ... role orchestrator phase timing event apply-start epoch $(date +%s)` when `next` returns `apply` after accept, and `event gate2 epoch ...` when it returns `gate2`; the reported numbers are the differences per run plus end-to-end (`created_at` → gate2), excluding human wait at Gate 0.

### D11. Release

`atlas bump skill openspec-orchestrator --minor -m "<notes>"` in the worktree (→ 1.4.0); commit whatever it writes; `releases.json` is never hand-edited. If it touches lines other than the new entry, report it at Gate 2 rather than editing the file.
